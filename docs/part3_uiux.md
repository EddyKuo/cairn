# 第三部分：UI/UX 設計規格（Cairn M0 · 無驅動單機 MVP）

| 項目 | 內容 |
|---|---|
| 版本 | v0.1 · 2026-08-19 |
| 適用範圍 | Cairn M0 單機 MVP（4 週可驗證），對應 spec v2.0 之方案 A / A+（純使用者模式 + Sysmon 選配增強） |
| 技術棧 | **`CairnConsole.exe`：MFC 宿主（`CWinAppEx`/`CFrameWndEx`）+ WebView2 填滿客戶區**；內層為 React 18 + Vite + TypeScript + TanStack Query，建置產物嵌入 EXE 資源 |
| 後端介面 | Named Pipe `\\.\pipe\Cairn\rpc`（JSON-RPC 2.0）連至 `CairnAgent.exe`；**不開任何監聽埠**。前端仍以 `fetch('/api/v1/...')` 撰寫，由 WebView2 的 `WebResourceRequested` 攔截轉接（見 §3.8.0） |
| 主要使用者 | P1 資安維運工程師 |
| 核心價值主張 | ①「5 分鐘內判斷告警真偽」 ②「告警看得懂」 |
| 明確不做 | 多端點管理、RBAC、mTLS、跨端點關聯查詢、報表匯出、行動版 |

> **UI 外殼與偵測核心的界線**：MFC 只負責「視窗這件事」——框架、系統匣、Toast、WebView2 初始化與其失敗退路、以及 RPC 轉接（完整清單見 §3.10）。所有畫面、導覽、狀態與互動皆在 React 內，**修改 UI 不需重新編譯 C++**。反向亦然：`CairnAgent.exe` 不含任何 MFC 型別（見 part0 §0.3 的界線宣告）。
>
> 這條界線讓本文件的其餘章節（線框、流程、tokens、元件、API 契約）**與宿主技術無關**——它們在瀏覽器、WebView2、或未來換成純 Win32 宿主下都一字不變。

## 3.1 資訊架構與導覽

### 3.1.1 導覽結構

```
CairnConsole.exe  (MFC 宿主視窗 · WebView2 客戶區 · 無監聽埠)
└── React SPA (in-process, 前端路由)
    ├── /alerts                    告警佇列        [預設首頁]
    │   └── /alerts/:alertId   告警詳情（含程序樹 + AI 敘事）
    ├── /telemetry             即時事件流
    └── /settings              設定
        ├── #exclusions        排除清單
        ├── #rules             規則狀態（唯讀 + 啟用/dry-run 切換）
        ├── #health            服務健康度
        └── #audit             稽核記錄
```

固定左側導覽列（寬 200px，可折疊為 56px 圖示列），頂部為全域狀態列。

> **導覽層級的歸屬**：上述導覽**全部由 React 前端負責**，MFC 宿主層不提供選單列、工具列或 MDI 分頁。宿主層只負責「視窗這件事」本身（框架、系統匣、Toast、初始化失敗的退路），其完整職責清單見 §3.10。這條界線讓 UI 的迭代不需重新編譯 C++。

### 3.1.2 為什麼只要這 4 個畫面

M0 的畫面數量是被「使用者的一個核心工作」反推出來的，不是被功能清單推出來的。P1 工程師的工作迴圈只有一個：**看到告警 → 判斷真偽 → 處置或標記誤報**。下列四個畫面各自對應這個迴圈中的一環（其中 **Live Telemetry 已移出 M0**，M0 實際交付三個畫面）：

| 畫面 | 對應迴圈環節 | 若砍掉會怎樣 |
|---|---|---|
| **Alerts 告警佇列** | 「有什麼要看」 | 沒有入口，產品不成立 |
| **Alert Detail** | 「這是不是真的」 | 判斷真偽必須看到完整程序樹與行為時序；沒有它就退化成一條看不懂的通知，直接違反核心價值主張 ② |
| **Live Telemetry**（**M1，M0 不交付**） | 「產品到底有沒有在跑」＋「這條規則為什麼沒命中」 | 原為規則調校與誤報排查的主要工具，因 C++ 的範圍重估而移出 M0（part4 §4.3.0）。M0 期間改以 `tools/Export-FpReport.ps1` 的離線報表 + `sqlite3` 直查取代——這是明確的能力降級，代價是誤報排查需離線分析 |
| **Settings** | 「別再吵我」＋「它還活著嗎」 | 誤報管理（part1 §3 U-03「誤報處置」）是 EDR 被解除安裝的頭號原因；Agent 健康度是無驅動架構下自我保護薄弱的唯一補償（被 kill 了要看得出來） |

**刻意排除的畫面與理由**：

- **Dashboard / 總覽圖表頁** — 單機環境下 KPI 圖表沒有決策價值（一台機器的「告警趨勢」是雜訊）。告警佇列頂部的四格統計條已足夠。這是 M0 最容易被要求加、但最沒有 ROI 的畫面。
- **報表 / 匯出頁** — 屬於 P3 資安主管的需求，M0 使用者是 P1。以 `GET /api/v1/alerts?format=csv` 的隱藏能力代替，不做 UI。
- **獨立的 Rules 管理頁** — M0 規則庫由我方隨產品發布，使用者不編輯規則，只需要「看得到有哪些規則、哪些在 dry-run」。降級為 Settings 的一個分頁。
- **Quarantine 隔離區頁** — M0 隔離動作次數極少，還原入口掛在 Settings 與稽核記錄的動作列即可。

**全域狀態列元素**：

- `DESKTOP-7F2A` — 本機 hostname
- `[🛡 防護中]` — 防護狀態徽章。三態：`防護中` / `僅記錄（學習期）` / `⚠ 已暫停 (12:34 剩餘)`。點擊展開暫停選單（15 分 / 1 小時 / 直到重開機），暫停需二次確認並寫入稽核。
- `[學習期 2/3 天]` — 僅在學習期內顯示，hover 顯示「學習期內僅記錄不阻擋，期滿將產出建議排除清單」，點擊跳至 Settings#exclusions
- `[◐ 主題]` — light / dark / system 三態切換
- `[⟳ 2s前]` — 最後同步時間，點擊強制重新整理

**側欄底部 Agent 健康度迷你面板**：無驅動架構下 agent 可被 taskkill，這個常駐指示燈是使用者察覺「防護已失效」的唯一途徑，因此固定顯示於每個畫面而非藏在 Settings。連線中斷時整條側欄底部轉為紅底並顯示「⚠ 無法連線至 Agent 服務，防護狀態未知」。

**MFC 宿主視窗行為**：

| 行為 | 規格 |
|---|---|
| 標題列 | 使用系統標準非客戶區，**不自繪**。標題固定為 `Cairn`，未讀高風險告警 > 0 時改為 `Cairn (3)` |
| 預設尺寸 | 1440×900；最小 1100×700（低於此寬度 Alert Detail 的雙欄會被迫堆疊，違反 §3.3 的分流時間預算） |
| 位置與大小記憶 | 關閉時寫入 `HKCU\Software\Cairn\UI`（`CWinAppEx::SaveState`），下次啟動還原；螢幕組態變更導致視窗落在畫面外時，回退至主螢幕置中 |
| 單一實例 | 具名 mutex `Global\CairnConsole.SingleInstance`；第二次啟動時啟用既有視窗（`SetForegroundWindow`）後立即結束 |
| 關閉鈕（✕） | **最小化至系統匣，不結束程序**。首次觸發時顯示一次性氣球提示「Cairn 仍在背景執行」。真正結束需由系統匣選單「結束 UI」 |
| 關閉 UI 的語意 | 結束 `CairnConsole.exe` **不影響 `CairnAgent.exe` 的偵測與回應**。系統匣選單的「結束 UI」須在確認對話框中明示這一點 |
| DPI | Per-Monitor V2；WebView2 自行處理縮放，MFC 端僅需在 manifest 宣告並正確處理 `WM_DPICHANGED` |
| 主題 | 前端的 light/dark 切換同步套用至 MFC 非客戶區（`DwmSetWindowAttribute` + `DWMWA_USE_IMMERSIVE_DARK_MODE`），避免深色內容配淺色標題列 |

**設計決策**：

- **雙行列（two-line row）**：第一行是機器可掃描的結構化欄位，第二行是人類可讀的「一句話發生了什麼」。這一句話由 Tier-2 規則的 `title` 欄位直接提供（**非 LLM 生成**，因此永遠即時可得），是「5 分鐘分流」能否成立的關鍵——使用者要能只看列表就篩掉 70% 的告警，不必每筆都點進去。
- **嚴重度以色塊 `▐█` + 文字雙重編碼**：不可只靠顏色，色盲使用者與列印稿都需要文字。
- **`AI` 欄三態**：`✓` 敘事已就緒（hover 顯示前 100 字）／`⏳` 生成中／`—` 未觸發（風險分數未達 80）。點擊直接跳至詳情頁的敘事區塊。
- **`規則命中` 欄的 `+2`**：表示除主要規則外另命中 2 條，hover 展開完整清單。避免列寬爆炸。
- **批次操作**（`[批次▾]`）：僅提供「標記為誤報」與「標記為已處理」兩項。批次執行回應動作（終止／隔離）在 M0 **刻意不提供**——不可逆動作不應支援批次，一次誤操作的代價太高。
- **排序**：預設「風險分數降冪 → 時間降冪」，而非純時間序。理由：分流工作的最佳順序是先看最危險的，不是先看最新的。表頭各欄可點擊改排序。
- **鍵盤操作**：`j/k` 上下移動、`Enter` 開啟詳情、`f` 標記誤報、`/` 聚焦搜尋、`Esc` 返回。SOC 分流是高重複性工作，鍵盤流是專業感的來源。

## 3.3 核心互動流程

### 3.3.1 主流程：5 分鐘告警分流

目標：從「收到告警」到「做出真偽判斷並完成處置」≤ 5 分鐘。以下逐步標註時間預算。

| # | 使用者看到什麼 | 使用者做什麼 | 系統回應什麼 | 預算 |
|---|---|---|---|---|
| 1 | 側欄「告警 12」徽章變紅並跳動一次；若視窗未聚焦，觸發系統通知「⚠ 嚴重告警：powershell.exe 注入 explorer.exe」 | 點擊通知或側欄徽章 | 導向 `/alerts`，新告警以短暫高亮底色（1.5s 淡出）標示 | 0:10 |

| 5 | 時間軸列出 5 個關鍵事件，其中 ② 顯示已封鎖的外連 IP | 展開事件 ② 查看完整命令列與目標 IP | 展開列顯示解碼後的 PowerShell（PowerShell 4104 ScriptBlock 提供的解混淆原文）、IP 的地理與威脅情報標記 | 2:30 |

**達成 5 分鐘的三個設計槓桿**：
1. **證據先於解釋**：左欄不等 AI，200ms 內可讀。若採「等 AI 生成完才渲染整頁」，光步驟 2 就吃掉 4–8 秒且無法預期。
2. **列表第二行的規則 `title`**：讓使用者在步驟 2 就完成 70% 的初步判斷，不必點開每一筆。
3. **`j/k` 不返回列表即可切換告警**：省去每筆 2 次的頁面往返（在 20 筆的佇列中累積可觀）。

### 3.3.3 子流程 B：執行回應動作 → 二次確認 → 稽核記錄

回應動作依可逆性分三級，對應三種不同的確認強度。**確認強度必須與破壞力匹配**——全部都用重確認會導致使用者盲目點過，全部都不確認則遲早出事。

> 動作識別碼一律為 C-9 的四個正規名。M0 **沒有**端點網路隔離（part1 §6），也沒有記憶體快照——
> 兩者都不在 part2 §2.7 的實作清單內。

| 級別 | 動作（C-9 正規名） | 可逆性 | 確認方式 | 需 prepare / token |
|---|---|---|---|---|
| L1 輕 | `suspend_process` | 完全可逆 | 直接執行 + Toast 含 `[復原]`（回應帶 `undo_token`） | **否**（缺 token 伺服器不拒絕） |
| L2 中 | `quarantine_file`、`firewall_block` | 可還原（隔離區保留原始檔與中繼資料；防火牆規則可刪） | 對話框 + 顯示影響 + 單次點擊確認 | **是**（token，不需打字） |
| L3 重 | `terminate_process_tree` | **不可逆**（已終止的程序無法復原） | 對話框 + 顯示完整影響清單 + **輸入根程序名確認** | **是**（token + `typed_confirmation`） |

L2/L3 缺 `confirmation_token` 一律回 `403 CONFIRMATION_REQUIRED`（§3.8.4）。

**`confirmation_token` 機制**：前端呼叫 `POST /api/v1/alerts/{id}/actions/prepare` 取得一次性 token（TTL 60 秒）與影響清單（要終止哪些 PID、有哪些警告）。實際執行時必須帶回該 token。這確保：① 對話框顯示的影響清單與實際執行的目標一致（不會因為期間程序樹變化而誤殺）② 無法透過直接呼叫 API 繞過確認流程 ③ 稽核記錄可證明使用者確實看過影響清單。這是 spec v2.0 §2.7「危險指令二次授權」在 REST 層的落實。

**二次授權的傳輸層保證**：`confirmation_token` 的比對在 `CairnAgent` 端完成，與 pipe 的 SDDL 存取控制正交。M0 **不實作應用層認證**，理由與作法見 §3.8.0；pipe SDDL 見 CONVENTIONS §C-2.3。⚠ M0 **不開任何監聽埠**，因此沒有 loopback HTTP、沒有 bearer token。

## 3.4 程序樹視覺化規格

程序樹是「5 分鐘判斷真偽」的主要證據來源，其設計品質直接決定產品是否達成核心價值主張。M0 採用**縮排樹（indented tree）而非節點圖（node graph）**：節點圖在超過 15 個節點後必然重疊糾結、需要 pan/zoom、且無法用鍵盤導覽；縮排樹可直接複用虛擬捲動、原生支援鍵盤與螢幕閱讀器、且列印/截圖後仍可讀（截圖貼進工單是 SOC 的高頻行為）。

### 3.4.1 節點的視覺結構

```
  ▲ powershell.exe          7712    96   ⛔ 已終止
  │  -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQA...          [⧉] [▸展開]
  │  🎯 R-T1055-001  T1059.001                    C:\Windows\System32\...\powershell.exe
  │  ⚠ 未簽章                                    14:22:01.220  存活 3.34s
```

| 元素 | 位置 | 規格 |
|---|---|---|
| **風險圖示** | 最左 | `▲` 高風險（≥80）／`●` 可疑（40–79）／`○` 正常（<40）／`⊘` 已排除。圖示 + 顏色雙重編碼 |
| **程序名** | 主標 | 14px medium。命中規則者加粗。**告警焦點程序**額外加左側 3px 色條 + 淺色背景 |
| **PID** | 右 1 | 12px mono muted。pid 會重用，hover 顯示完整 `process_guid` |
| **風險分數** | 右 2 | 12px mono，以分數對應的 severity 色著色。**這是分數而非布林**，直接反映 Tier-2 的加權計分設計 |
| **狀態徽章** | 右 3 | `⛔ 已終止`（我方動作）／`⏸ 已暫停`／`● 執行中`／`✓ 已結束`（自然結束）／`⛔ 已阻擋`（未啟動） |
| **命令列** | 第 2 行 | 12px mono，單行截斷 120 字元。`[⧉]` 一鍵複製完整命令列。**若含 `-enc`/Base64，額外顯示 `[🔓 解碼]`**，解碼結果來自 PowerShell 4104 ScriptBlock 的解混淆原文，這是 M0 最高價值的單一微互動 |
| **規則命中** | 第 3 行 | `🎯` + 規則 ID 膠囊，可點擊 → 捲動至右欄該規則卡片並高亮 |
| **簽章狀態** | 第 4 行 | `✓ 已簽章 (Microsoft Corporation)` 綠／`⚠ 未簽章` 黃／`✗ 簽章無效` 紅。**簽章者是最強的降誤報訊號**，必須永遠可見而非藏在展開區 |
| **映像路徑** | 第 3 行右 | 12px mono muted，中段省略（`C:\Windows\…\powershell.exe`），hover 顯示完整 |
| **時間** | 第 4 行右 | 建立時間（毫秒精度）+ 存活時長 |

**非程序節點（注入邊）**：遠端執行緒注入不是父子關係，以虛線分支 + 特殊圖示表示：
```
  ▲ powershell.exe   7712   96
    ├ ╌╌▶ [遠端執行緒注入] → explorer.exe (1204)   ⛔ 已阻擋   14:22:04.560
```
點擊該邊會**同時高亮來源與目標兩個節點**，並在時間軸上標記該事件。

### 3.4.2 大型程序樹的折疊策略

M0 定義的預設可見集合為「**攻擊路徑 + 一層脈絡**」，其餘全部折疊。演算法：

1. **必定展開**：從樹根到告警焦點程序的完整路徑（ancestor chain）。
2. **必定展開**：焦點程序的所有風險分數 > 0 或有規則命中的後代。
3. **展開一層**：焦點程序的直接子程序（即使風險為 0），提供脈絡。
4. **摺疊為摘要列**：其餘同層節點合併為 `⋯ 另有 N 個低風險子程序 [展開]`。
5. **硬性上限**：預設渲染節點數上限 200。超出時以虛擬捲動（`@tanstack/react-virtual`）處理，並在頂部顯示「此程序樹共 1,842 個節點，已依風險摺疊顯示 200 個 [顯示全部（可能較慢）]」。

**噪音抑制**：`svchost.exe`、`conhost.exe`、`RuntimeBroker.exe` 等已知高頻低價值程序，在風險為 0 且無規則命中時預設併入摘要列。此清單隨規則包更新，使用者可於 Settings 關閉此行為。

**工具列**：`[展開全部]`／`[僅顯示攻擊路徑]`／`[⤢ 全螢幕]`／`[⤓ 匯出 PNG]`。`[僅顯示攻擊路徑]` 是製作工單截圖時的常用視圖。

### 3.4.3 鍵盤與無障礙

- 樹以 `role="tree"` / `role="treeitem"` + `aria-expanded` / `aria-level` 標記。
- `↑↓` 移動、`←` 折疊或跳至父節點、`→` 展開或跳至第一個子節點、`Enter` 展開節點詳情、`Home/End` 首末節點。
- 風險等級同時以 `aria-label` 表述（「嚴重風險，分數 96」），不依賴顏色。

### 3.4.4 時間軸與程序樹的同屏關聯

兩者共用一組 **process lane 色彩**（依 process_guid 雜湊決定，同一程序在兩個元件中永遠同色），並以三種互動建立關聯：

| 互動 | 程序樹的反應 | 時間軸的反應 |
|---|---|---|
| **hover 程序樹節點** | 節點高亮 | 該程序的 lane 提亮，其他 lane 降至 30% 不透明度；該程序的事件標記放大 |
| **hover 時間軸事件標記** | 對應程序節點高亮並自動捲入視野 | 顯示事件 tooltip（時間、類型、目標、命中規則、加分） |
| **點擊時間軸事件** | 對應節點選取並展開 | 下方事件清單捲動至該事件並展開 |
| **拖曳時間軸選取區間** | 區間外無事件的程序節點降為 40% 不透明度 | 下方事件清單篩選為該區間 |

**時間軸規格**：
- X 軸為時間，預設視窗為「告警觸發時刻 ±30 秒」，可用 `[載入前 60 秒]` / `[載入後 60 秒]` 延伸，或拖曳底部的 range slider 縮放。
- Y 軸為程序 lane，順序與程序樹的可見順序一致（視覺上左右對齊）。
- 事件標記：`●` 一般事件、`▲` 規則命中事件、`⛔` 我方回應動作。標記大小依風險加分放大。
- 事件密度過高時（同一像素 >5 個事件）自動聚合為 `▮` 密度條，hover 顯示「此處有 47 個事件」，點擊放大該區間。
- **關鍵事件永不聚合**：規則命中與回應動作永遠獨立渲染，即使重疊。

## 3.5 AI 敘事區塊呈現規格

這是全產品在**產品倫理與架構誠實性**上最關鍵的一塊 UI。設計目標有二：① 讓敘事真的有用（降低對資深 SOC 人力的依賴，差異化主張 ②）② 讓使用者絕不誤以為 AI 在做決策（架構上 LLM 無阻擋權，UI 必須如實反映）。

### 3.5.1 免責標示（強制、不可關閉）

固定於敘事區塊最頂部，**不可折疊、不可 dismiss、不隨捲動消失**（sticky）：

```
┌────────────────────────────────────────────────────────┐
│ ⓘ 本敘事由本機 LLM 生成，僅供理解與分流參考。它未參與、│
│   也無權參與任何偵測或阻擋決策——本次阻擋由規則         │
│   R-T1055-001 與風險分數 96 觸發。                       │
└────────────────────────────────────────────────────────┘
```

**設計要求**：
- 第二句的後半段是**動態填入的實際決策依據**（規則 ID + 分數），不是固定文案。這讓免責標示同時具有資訊價值，使用者不會養成跳過它的習慣——這是免責標示能長期有效的唯一辦法。
- 樣式為低飽和的資訊色底＋1px 邊框，字級 13px。刻意不用警告色（黃/紅），避免與真正的風險訊號競爭注意力。
- 整個右欄以 `🤖` 圖示與虛線左邊框標示為「AI 生成區」，與左欄的確定性證據在視覺上明確分區。

**規格細節**：

- **敘事長度硬性上限 200 字**（約 3 段）。超過的內容使用者不會讀，且長輸出增加 LLM 逾時風險。以 GBNF 文法在生成階段約束，而非在 UI 截斷。
- **段落結構固定為三段**：`發生了什麼` → `為什麼可疑` → `這意味著什麼`。固定結構讓使用者第 5 次讀時能直接跳到需要的段落。
- **敘事中的實體自動連結**：程序名、檔案路徑、IP 位址在敘事文字中偵測並轉為可點擊連結，點擊後高亮程序樹/時間軸上的對應項。此連結由前端在**已驗證的實體白名單**上做比對（白名單來自該告警的實際遙測資料），**不是**讓 LLM 自由輸出 HTML——LLM 輸出一律當作純文字渲染，杜絕輸出端注入。
- **建議處置明確標示「系統不會自動執行」**：避免使用者誤以為建議已被套用。
- **ATT&CK 標籤可點擊**：開啟 `https://attack.mitre.org/techniques/T1566/001/`（新分頁）。離線環境下改為顯示內建的技術描述彈窗（規則包隨附精簡 ATT&CK 資料），**不可出現斷開的連結**——氣隙可用是核心賣點，UI 不能有任何一處假設有網路。
- **信心分數以進度條 + 數值 + 文字三重呈現**：`≥0.8 高`（正常色）／`0.5–0.79 中`（黃）／`<0.5 低`（黃 + 附加提示「模型對此判斷信心偏低，請以左欄證據為準」）。
- **模型 ID 與雜湊永遠顯示**：對應 part2 §2.6.2「模型版本凍結」與差異化主張 ③「可稽核的自主性」。任何一段 AI 產出都能追溯到確切的權重檔。
- **`[👍/👎]` 回饋直接餵入 part1 §4 M-07 的「告警敘事有用性評分 ≥ 4.0/5.0」指標**。點 `👎` 展開可選原因（不正確／太籠統／與證據矛盾／看不懂）。

### 3.5.3 三種非就緒狀態

**狀態 1：生成中（pending）**

```
┌────────────────────────────────────────────────────────┐
│ ▼ 🤖 AI 攻擊敘事                                       │
│ ┌ [免責標示] ────────────────────────────────────────┐ │
│ └────────────────────────────────────────────────────┘ │
│                                                        │
│         ⏳  正在生成攻擊敘事…  3.2s                    │
│         ▓▓▓▓▓▓▓▓░░░░░░░░░░░  預計 20 秒內完成          │
│                                                        │
│   ⓘ 左欄的程序樹與事件時間軸已完整可用，               │
│      您可以先開始判讀，不需等待此區塊。                │
│                                                        │
│                                       [取消生成]       │
└────────────────────────────────────────────────────────┘
```
- 骨架屏 + 已耗時計數器（秒，每 100ms 更新）。
- **明確告知「不必等」**：這句提示是達成 5 分鐘分流的關鍵，它防止使用者陷入盯著轉圈的等待。
- 前端一律以 **2 秒輪詢** `GET /api/v1/alerts/{id}/narrative` 取得結果（端點 4）。串流為 M1 預留（`"streaming"` 於 M0 恆為 `false`，SDD-03 §9.6）——M0 不實作 SSE 敘事串流，也沒有對應的 RPC method。
- 超過 20 秒（part2 §2.8 M0-P8 的 CPU P95 目標）進度條轉黃並顯示「較預期慢，可能因為模型正在載入」；30 秒（part2 §2.6.5 的總逾時）判定為 timeout。

**狀態 2：失敗（failed）**

```
┌────────────────────────────────────────────────────────┐
│ ▼ 🤖 AI 攻擊敘事                                       │
│                                                        │
│   ⚠  無法生成攻擊敘事                                  │
│                                                        │
│   原因：模型輸出未通過 JSON Schema 驗證（已重試 2 次） │
│   錯誤碼：SCHEMA_VIOLATION                             │
│                                                        │
│   ⓘ 這不影響偵測結果。本次告警由規則 R-T1055-001         │
│      與風險分數 96 觸發，阻擋動作已正常執行。          │
│      左欄的完整證據不受影響。                          │
│                                                        │
│              [↻ 重試]  [檢視原始輸出]  [回報問題]      │
└────────────────────────────────────────────────────────┘
```
- 錯誤碼對應後端 `InferError` 列舉：`ModelLoadFailed` / `OutOfVram` / `SchemaViolation` / `ContextOverflow` / `NotInitialized`。每種都有人話說明與對應建議動作（例如 `OutOfVram` → 「顯示記憶體不足，已自動降級至 CPU 模式，可於設定調整」）。
- **失敗訊息必須主動聲明「這不影響偵測結果」**。否則使用者會誤以為防護失效——這是無經驗使用者最常見的誤解，也是最容易導致產品被解除安裝的認知失誤。
- `[檢視原始輸出]` 開啟開發者用抽屜，顯示未通過驗證的原始 LLM 輸出與 schema 錯誤位置。M0 階段這是調校 GBNF 文法的主要工具。

**狀態 3：逾時（timeout）**

```
┌────────────────────────────────────────────────────────┐
│ ▼ 🤖 AI 攻擊敘事                                       │
│                                                        │
│   ⏱  敘事生成逾時（31.2s > 上限 30.0s）                │
│                                                        │
│   已取消以避免佔用分析佇列。                           │
│   常見原因：模型首次載入、CPU 模式下的長事件序列、     │
│            系統正處於高負載。                          │
│                                                        │
│   ⓘ 偵測與阻擋完全不受影響。                           │
│                                                        │
│   [↻ 重試]   [↻ 以較短脈絡重試]   [不再為此告警生成]   │
└────────────────────────────────────────────────────────┘
```
- **逾時與失敗必須是不同狀態**：逾時是資源問題（重試可能成功、且有「縮短脈絡」這個特有的補救手段），失敗是輸出品質問題（重試同樣參數多半再次失敗）。混為一談會給出無效的補救建議。
- `[以較短脈絡重試]` 將事件序列裁減至最關鍵的 5 個事件後重送，是 CPU 模式下最有效的補救。
- 逾時事件同時寫入 Settings#health 的「過去 24 小時異常」清單，供使用者發現系統性的效能問題。

**三種狀態的共同規則**：
1. 免責標示在所有狀態下都存在（包括失敗狀態），維持一致的心智模型。
2. 每種狀態都必須明說「不影響偵測/阻擋」。
3. 左欄永不因右欄狀態而改變——這是架構承諾在 UI 上的可驗證體現。
4. 三種狀態均不阻擋 `[✓ 標記為已處理]` 等任何工作流程操作。

### 3.7.2 狀態規範

每個資料驅動元件必須實作 **5 種狀態**，缺一不可（Code Review 檢查項）：

**① 載入中 (Loading)**
- 一律使用**骨架屏**，不使用轉圈 spinner——骨架屏能傳達即將出現的內容結構，減少版面跳動（CLS）。
- 骨架形狀必須貼合實際內容（告警列 = 兩行灰條；程序樹 = 縮排階梯狀灰條）。
- 骨架動畫為 1.4s 的 shimmer；`prefers-reduced-motion` 時改為靜態底色。
- **超過 3 秒**額外顯示「載入時間較長…」與 `[取消]`。
- **不使用全頁載入**：已可得的區塊立即渲染。詳情頁左欄先出、右欄後出，是這條規則最重要的應用。

**② 空狀態 (Empty)** — 每個空狀態都必須回答「為什麼是空的」與「我該做什麼」

| 位置 | 圖示 | 主標 | 副標 | 動作 |
|---|---|---|---|---|
| 告警佇列（真的沒告警） | 🛡 | 目前沒有待處理的告警 | 防護持續運作中，已監控 3 天 04 小時。最後一筆告警為 2 天前。 | `[檢視已處理告警]` |
| 告警佇列（篩選後為空） | 🔍 | 沒有符合條件的告警 | 目前篩選：嚴重度=嚴重、時間=24 小時內 | `[清除篩選]` |
| 事件流（篩選語法無結果） | ≋ | 過去 60 秒沒有符合的事件 | 串流持續進行中，符合條件的事件出現時將自動顯示 | `[放寬篩選]` |
| 排除清單（無排除） | ✓ | 尚未建立任何排除規則 | 標記告警為誤報時可一併建立排除規則，或直接手動新增。 | `[+ 新增排除]` |
| 稽核記錄（無記錄） | 📋 | 此期間內沒有稽核記錄 | 所有回應動作與設定變更都會記錄於此。 | `[擴大時間範圍]` |
| 程序樹（僅單一程序） | — | *不顯示空狀態* | 直接渲染單節點；「只有一個程序」本身就是有意義的資訊 | — |

## 3.8 REST API 契約草案（M0）

### 3.8.0 傳輸層：REST 形狀，Named Pipe 實體

**前端程式碼一律以 `fetch('/api/v1/...')` 撰寫，本節的契約完全不變。** 但這些請求**不會離開程序、也不會經過任何 TCP 埠**：

```
React fetch('/api/v1/alerts/{id}')
        │
        ▼
WebView2  ICoreWebView2::add_WebResourceRequested        ← 攔截 (filter: "*://cairn.local/api/v1/*")
        │
        ▼
CairnConsole.exe  RpcBridge：HTTP 語意 → JSON-RPC 2.0 method + params
        │
        ▼
Named Pipe  \\.\pipe\Cairn\rpc   (4-byte LE 長度前綴，SDDL 見 CONVENTIONS.md C-2)
        │
        ▼
CairnAgent.exe  RpcServer → 對應處理器 → JSON 結果
        │
        └──► 回程封裝為 ICoreWebView2WebResourceResponse（含 status / headers / body）
```

**為什麼不讓服務直接開一個 loopback HTTP 埠**（這是更省事的作法，但被否決）：

| 理由 | 說明 |
|---|---|
| 不擴大攻擊面 | 本機任何一個低權限程序、任何一個瀏覽器分頁的 JS，都能連上 `127.0.0.1` 的監聽埠。這正是 v2 §2.2 A5 所描述的攻擊面；而 Named Pipe 可用 SDDL 做**核心層級**的存取控制，不需要自建認證 |
| 不需要發明認證機制 | HTTP 方案得自己做 token 產生、儲存、輪替、比對，且 token 檔一旦被讀走就失效。Pipe 方案由 OS 依呼叫端 token 判定，**沒有可被竊取的祕密** |
| 免疫 DNS rebinding 與 CSRF | 沒有 origin、沒有 cookie、沒有瀏覽器，這整類攻擊不存在 |
| 不佔埠、不觸發防火牆提示 | 免去與其他軟體搶埠，以及 Windows 防火牆在安裝時彈窗要求授權（會嚇到採購方） |

**代價與處置**：前端在 Vite dev server（`npm run dev`）下沒有 WebView2 攔截層，因此開發模式改用 MSW（Mock Service Worker）或 `CairnConsole.exe --dev-http 5080` 這個**僅供開發、預設不編譯進 Release** 的旗標。此旗標在 Release 組態下以 `#ifdef` 完全移除，不是執行期開關。

**通用約定**

| 項目 | 規格 |
|---|---|
| Base URL | `/api/v1`（相對路徑；WebView2 內的虛擬主機為 `https://cairn.local`） |
| 傳輸 | Named Pipe `\\.\pipe\Cairn\rpc`，JSON-RPC 2.0，4-byte LE 長度前綴 |
| 認證 | **無應用層認證**。存取控制由 pipe 的 SDDL 於 OS 層完成；危險動作另需 `confirmation_token`（見 §3.8.4） |
| 內容類型 | `application/json; charset=utf-8`；串流端點改以 JSON-RPC 通知（server→client push）實作，前端仍以 `EventSource` 介面消費（由 RpcBridge 轉接） |
| 時間格式 | RFC3339 UTC，毫秒精度（`2026-08-19T06:22:07.412Z`） |
| 分頁 | `?limit=20&cursor=<opaque>`，回應含 `next_cursor`（無下一頁時為 `null`）與 `stats.total_matched`。⚠ **單向 opaque cursor，沒有回退能力**，因此列表 UI 用「載入更多」而非頁碼——頁碼式分頁在 cursor 模型下無從計算 |
| 錯誤格式 | `{ "error": { "code": "SCHEMA_VIOLATION", "message": "人類可讀說明", "details": {} } }`；JSON-RPC 層的錯誤由 RpcBridge 映射為對應 HTTP 狀態碼 |
| 服務未連線 | RpcBridge 回傳 `503` + `{"error":{"code":"SERVICE_UNAVAILABLE"}}`，前端據此進入 §3.10 的「服務失聯」全頁攔截 |
| **分數單位** | API **一律回傳 0–100 的顯示分（整數）**，由 `CairnAgent` 的 RPC 處理器自 milli-point（part2 §2.3.2，`kScoreScale=1000`）四捨五入換算。前端不做任何分數運算；原始 milli-point 只存在於 DB 與規則引擎內部 |
| **動作識別碼** | 一律使用 CONVENTIONS §C-9 的四個正規名：`suspend_process` / `terminate_process_tree` / `quarantine_file` / `firewall_block`。`actions_taken[].action`、`timeline[].action_taken`、`POST /actions` 的 `action` 三處共用同一組枚舉 |
| **`confirmation_token` 的適用範圍** | L1 動作免 token（直接 `POST /actions`，回應含 `undo_token`）；L2 需 token；L3 需 token + `typed_confirmation`。L2/L3 缺 token 一律回 `403 CONFIRMATION_REQUIRED`（見 §3.3.3 的分級表） |

**JSON-RPC → HTTP 錯誤碼映射**（RpcBridge 的完整對照，前端據此寫統一錯誤處理）：

| JSON-RPC | HTTP | code |
|---|---|---|
| `-32601` method not found | 404 | `NOT_FOUND` |
| `-32602` invalid params | 400 | `INVALID_PARAMS` |
| `-32603` internal error | 500 | `INTERNAL` |
| pipe 無法連線 | 503 | `SERVICE_UNAVAILABLE` |
| pipe 逾時（> 5 s） | 504 | `RPC_TIMEOUT` |
| 業務錯誤 | 由處理器指定（409 / 410 / 422 / 403） | 見 §3.8.4 |

所有非 2xx 一律帶上方的 error 物件。

## 3.10 原生宿主層的 UI 職責

本節是本文件中**唯一與宿主技術相依**的章節，規範 `CairnConsole.exe` 的 MFC 層必須自己畫、自己管的東西。判準只有一條：**WebView2 畫不出來、或 WebView2 還沒活著的時候需要的東西，才屬於宿主層。** 其餘一律屬於 React。

### 3.10.1 系統匣圖示（四態）

無驅動架構下服務可被 taskkill（part1 §6 已誠實揭露），系統匣圖示因此不只是捷徑，而是**使用者察覺「防護已失效」的最後一道途徑**——它必須在主視窗關閉時仍然說得出實話。

| 狀態 | 圖示 | Tooltip | 觸發條件 | 使用者可做什麼 |
|---|---|---|---|---|
| **防護中** | 🛡 藍盾（實心） | `Cairn — 防護中`<br>`事件 4.2k/s · 今日告警 3` | RPC 通、Sysmon 服務 Running、事件率 > 0 | 正常操作 |
| **學習期** | 🛡 藍盾 + 沙漏角標 | `Cairn — 學習期 2/3 天`<br>`僅記錄，不執行回應動作` | 安裝後 3 天內（part2 §2.5） | 點擊跳 Settings#exclusions |
| **降級** | ⚠ 琥珀盾 | `Cairn — 能力降級`<br>`Sysmon 未執行，僅剩粗粒度事件` | RPC 通，但 Sysmon 停用／config 漂移／事件率為 0／丟包 > 5%／LLM 不可用 | 點擊跳 Settings#health，該處列出**具體哪一項降級與修復指令** |
| **服務失聯** | ✕ 紅盾（灰底） | `Cairn — 防護狀態未知`<br>`無法連線至 CairnAgent 服務` | RPC 連續 3 次失敗（約 5 秒） | 右鍵選單提供「嘗試啟動服務」（`sc start CairnAgent`，需提權，會跳 UAC） |

**設計約束**：
- 圖示狀態由 MFC 層**獨立輪詢**（每 2 秒一次 `health` RPC），**不依賴 WebView2 是否已載入**。主視窗關閉、WebView2 崩潰、或前端 JS 例外時，托盤狀態必須仍然正確。
- 狀態**只降不升的遲滯**：由「防護中」轉為其他狀態立即生效；由異常態恢復為「防護中」需連續 3 次健康檢查通過，避免圖示閃爍。
- 降級與失聯態在**首次進入時**各顯示一次氣球通知；同一狀態不重複騷擾（除非中間曾恢復正常）。

### 3.10.2 Toast 通知

| 項目 | 規格 |
|---|---|
| 觸發條件 | 新告警且 `risk_score >= 80`。分數 40–79 **不通知**（只進佇列），否則學習期的雜訊會讓使用者關掉通知，通知就永久失效了 |
| 實作 | Windows 10+ 原生 Toast（`ToastNotificationManager`，需 AUMID 與捷徑註冊）；註冊失敗時退回 `Shell_NotifyIcon` 氣球提示 |
| 內容 | 標題＝規則標題（如「Office 產生腳本直譯器並注入其他程序」）；內文＝`程序名 · 分數 · 時間`；**不放 AI 敘事**（生成中，且 §3.5 的免責標示在 Toast 中無處安放） |
| 動作 | 主體點擊 → 啟用主視窗並直達 `/alerts/{id}`（若視窗在托盤則先還原）。次要按鈕「稍後處理」→ 僅關閉 |
| 節流 | 同一 `process_tree_root` 60 秒內最多 1 則；全域每分鐘上限 3 則，超出者合併為「另有 N 則新告警」 |
| 靜音 | Settings 可關閉 Toast，但**系統匣圖示狀態不可關閉** |

| 元素 | 規格 |
|---|---|
| 「偵測服務不受影響」 | **必要**。否則使用者會以為防護整個掛了而去重裝甚至移除 |
| 服務狀態列 | 由 MFC 直接走 RPC 取得並以 `CStatic` 繪出——這是 WebView2 死亡時使用者唯一能看到的即時資訊 |
| 「安裝 WebView2…」 | 開啟隨產品附帶的 `redist/MicrosoftEdgeWebview2Setup.exe`（離線／氣隙環境是目標場景，**不可只給一個下載連結**）。安裝完成後自動重試 |
| 「複製錯誤詳情」 | HRESULT、Runtime 版本查詢結果、`%LOCALAPPDATA%\Cairn\ui.log` 末 50 行，一次複製到剪貼簿 |
| 重試 | 不重啟程序，重新呼叫 `CreateCoreWebView2Environment`；連續 3 次失敗後按鈕改為「重新啟動 CairnConsole」 |
| WebView2 中途崩潰 | 監聽 `ICoreWebView2::add_ProcessFailed`；`BrowserProcessExited` 自動重建一次並回到原路由，第二次失敗才落到本畫面 |

### 3.10.4 服務失聯時 WebView2 內顯示什麼

WebView2 活著、但 `CairnAgent` 沒回應（RpcBridge 回 `503`）時，錯誤畫面畫在**前端**，規格如下（對應 §3.9 驗收條件 U-07）：

| 項目 | 規格 |
|---|---|
| 觸發 | 任一 API 連續 3 次收到 `503 SERVICE_UNAVAILABLE`（約 5 秒） |
| 呈現 | **全頁攔截**（非 toast、非橫幅）。理由：此時畫面上所有數字都是過期的，繼續顯示等同說謊 |
| 文案 | 標題「防護狀態未知」；內文「無法連線至 Cairn 服務。這可能是服務已停止、當機、或被終止。**在恢復前，本機不受保護。**」 |
| 保留可見的資料 | 全部灰階化並疊上「資料截止於 HH:MM:SS」浮水印，**不清空**——分析師可能正在讀某筆告警 |
| 動作 | 「重試連線」（立即重試）／「嘗試啟動服務」（走 MFC 提權，會跳 UAC）／「查看疑難排解」（開啟本機說明頁） |
| 自動恢復 | 背景每 5 秒重試；恢復後自動移除攔截、重新取數、並在頂部顯示一次性提示「已恢復連線（中斷 2 分 14 秒）」 |
| 側欄健康度面板 | 同步轉為紅底（§3.2.1 已定義），兩者一致 |

> **與 §3.5「AI 敘事不可用」的區別**：LLM 掛掉只讓右欄降級，左欄證據完全可讀，**不攔截**；服務掛掉則所有資料都不可信，**必須攔截**。這個差別正是「證據與解釋分離」在錯誤處理上的延伸。

### 3.10.5 宿主層的明確非職責

| 不做 | 理由 |
|---|---|
| MFC 選單列、工具列、狀態列 | 全部由 React 繪製，避免兩套視覺語言 |
| MFC 對話框（設定、確認、關於） | 回應動作的二次確認在 §3.3.3 已定義為前端對話框，需顯示影響清單，MFC 畫不出來也不該畫 |
| 任何偵測、計分、規則邏輯 | 一律在 `CairnAgent`。UI 被關閉或崩潰不得影響偵測 |
| 本機快取資料庫 | UI 無狀態，所有資料每次經 RPC 取得 |

## 附註：M0 未涵蓋、須於 R1.0 補上的 UI 議題

1. **多端點檢視**：告警佇列的 hostname 欄、端點健康度總覽、跨端點行為關聯查詢。M0 的元件已預留 `agent_id`/`hostname` 欄位，資料模型不需改動。
2. **RBAC**：檢視者角色下需隱藏所有回應動作按鈕（而非停用），Settings 改唯讀。
3. **R1.0 的遠端檢視**：若需中央主控台，前端須自 Named Pipe 轉接改為真正的 HTTP + mTLS。因此 M0 階段即須將所有 API 呼叫收斂至單一 `apiClient` 模組，使此遷移為單檔改動。（M0 的 WebView2 宿主與 Named Pipe 轉接已於 §3.8.0 落地，不屬本清單。）
4. **報表匯出 UI**：對應 P3 資安主管的稽核需求（CEF / OCSF）。
5. **驅動架構下的新 UI**：取得 ELAM 後，Settings#health 的「自我保護能力揭露」區塊需改寫為正面表述，程序樹需支援「已於建立前阻擋」的新狀態（M0 不存在此狀態）。
